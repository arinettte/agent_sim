# Методы и подробности эксперимента

Технический справочник к [README](../README.md): точный протокол, метрики, ограничения, история пилота и разведочный анализ. Пути к файлам ниже указаны от корня репозитория. Логи пилота лежат в `results/pilot/`.

## Запуск

Все команды выполняются из корня проекта. Используется существующая `.venv`, HTTP — стандартная библиотека Python. Для графика нужен matplotlib; программа ничего не устанавливает. Ollama должен уже работать на localhost:11434, модель должна быть доступна локально. Сервер и загрузка моделей здесь не запускаются.

```bash
.venv/bin/python -m unittest -v
.venv/bin/python lab.py prompts
# Только после разрешения доступа к Ollama: smoke, один прогон на условие
.venv/bin/python lab.py run --runs 1 --log results/smoke.jsonl
.venv/bin/python lab.py analyze --log results/smoke.jsonl --output results/smoke-analysis
# Полный эксперимент: по 20 прогонов на условие
.venv/bin/python lab.py run
.venv/bin/python lab.py analyze
# Запасная модель; тот же аргумент необходим при анализе
.venv/bin/python lab.py run --model qwen3:1.7b --log results/fallback.jsonl
.venv/bin/python lab.py analyze --model qwen3:1.7b --log results/fallback.jsonl
```

Число прогонов меняется через `--runs`. Для продолжения повторите команду: завершённые пары «номер прогона, условие» с точно совпадающей конфигурацией пропускаются. Smoke сохраняется отдельно от основного эксперимента. Одновременная запись нескольких процессов в один лог не поддерживается.

## Полный запуск зафиксированного протокола v3

Команды выполняются из корня проекта. Запуск и возобновление используют одну команду; `tee -a` дописывает прогресс после каждого завершённого прогона в full.out и показывает его в терминале. При совпадении конфигурации завершённые agreed и failed не повторяются. Не запускайте два процесса записи в один лог одновременно.

```bash
mkdir -p results
set -o pipefail
.venv/bin/python -u lab.py run --model qwen3:4b-instruct --runs 20 --log results/full.jsonl 2>&1 | tee -a results/full.out
```

После завершения:

```bash
MPLCONFIGDIR="$PWD/results/.mplconfig" .venv/bin/python lab.py analyze --model qwen3:4b-instruct --log results/full.jsonl --output results/full-analysis
```

Проверка прогресса в другом терминале (без запросов к модели; считаются уникальные завершённые прогоны текущей конфигурации):

```bash
.venv/bin/python - <<'PY'
from pathlib import Path
import lab

config = dict(lab.DEFAULTS, model='qwen3:4b-instruct')
done = {(r['index'], r['condition'])
        for r in lab.read_logs(Path('results/full.jsonl'))
        if r.get('config') == config
        and r.get('config_id') == lab.config_id(config)
        and r.get('status') in ('agreed', 'failed')
        and type(r.get('index')) is int and 0 <= r['index'] < 20
        and r.get('condition') in ('no_memory', 'memory')}
for condition in ('no_memory', 'memory'):
    print(f'{condition}: {sum(c == condition for _, c in done)}/20')
print(f'Всего: {len(done)}/40')
PY
```

При прерывании незавершённый прогон выполняется заново. Продолжение проверено unittest: после имитации сбоя и оборванной строки повторяется только недостающее условие, следующая попытка полностью пропускает завершённые прогоны, файл не меняется. Отдельно проверено, что другая конфигурация и незавершённый статус не считаются выполненными. HTTP в этих тестах заблокирован заглушкой.

## Методология

Агенты A, B, C предлагают по кругу, максимум 8 раундов. A максимизирует собственную долю с возможностью компромисса, B не принимает меньше 40, C предпочитает близкое к 33/33/34 распределение. Предложение — целые неотрицательные числа с суммой 100. Предлагающий голосует за автоматически; два других голосуют последовательно, не видя голосов текущего раунда. Требуется единогласие; при провале после восьми раундов каждый получает 0. В каждом запросе указано число оставшихся раундов, включая текущий. Невалидное предложение B с его долей меньше 40 также отклоняется: автоматический голос иначе нарушал бы его ограничение.

Без памяти запрос содержит только приватную роль, общие правила, номер раунда и текущее предложение при голосовании. С памятью добавляется публичная история предыдущих завершённых раундов: предложения, их публичные reason и голоса. Каждый агент получает отдельный свежий контекст; приватные инструкции других агентов, ответы с ошибками и результаты повторных попыток в публичную историю не попадают. Общие правила присутствуют в обоих условиях.

Все запросы идут последовательно только через `/api/chat`, с `stream: false`, JSON-схемой в `format` и HTTP-таймаутом 180 секунд. Параметры собраны в `DEFAULTS` в lab.py: temperature=0.4, num_predict=180, num_ctx=8192. Основная модель qwen3:4b-instruct; для qwen3:1.7b передаётся think=false. Seed=1729+номер прогона (нумерация с нуля), одинаковый для всех обращений в паре условий. Порядок условий чередуется по номерам прогонов для уменьшения влияния прогрева.

JSON разбирается и проверяется локально: типы, ключи, границы, сумма и ограничение B. Голос задаётся полем `vote` со значением `accept` или `reject`. reason должен быть строкой, но его длина, язык и число предложений не влияют на валидность. В промпте запрошено объяснение на русском, не длиннее 15 слов. Только при записи JSONL reason обрезается до 200 символов, включая вложенные копии в истории и JSON-тексте ответа; контекст текущего прогона не обрезается. Поле raw сохраняет JSON ответа с обрезанным reason, а не побайтовый оригинал; неразбираемый JSON сохраняется как получен. После любой ошибки — одна повторная попытка с тем же контекстом. Затем предложение пропускается или голос считается против. Доли и ответы не исправляются.

Каждая строка JSONL — один завершённый прогон со всеми раундами, запросами, ответами с обрезанным reason, длительностями, seed и полной конфигурацией. Ошибки разделены на json, schema, game и transport. Невалидные первичные ответы, повторы и окончательно невалидные действия сохранены отдельно. Запись сбрасывается на диск после каждого прогона. При аварии незавершённый прогон выполняется заново; повреждённая строка пропускается с предупреждением. Идентификатор конфигурации включает версию протокола: при изменении промптов, схем или логики нужно увеличить `version` в DEFAULTS. Изменение числа требуемых прогонов не меняет конфигурацию.

## Зафиксированный план оценки до полного запуска

Основная метрика — доля accept среди двух голосующих, без автоматического голоса предлагающего: суммарное число accept / число фактически запрошенных голосов в условии. Для окончательно невалидного голоса используется reject, как в игре; повторы не увеличивают знаменатель. Дополнительно показывается траектория этой доли по раундам. Завершённые соглашением прогоны больше не создают голосов, поэтому состав поздних раундов меняется.

Вторичные метрики — доля соглашений; число почти-соглашений (валидных предложений ровно с одним итоговым reject); уступчивость агентов (изменение собственной доли в их последовательных предложениях); Джини предложений по раундам. Число почти-соглашений показывается суммарно и по прогонам. Ранее добавленные метрики успешных распределений, времени до сделки и невалидных ответов сохраняются как дополнительные. Выбор основной метрики сделан после пилота, до полного эксперимента; пилотные результаты не являются подтверждающей проверкой гипотезы.

## Метрики и анализ

`summary.json` содержит для каждого условия число прогонов и:

- долю соглашений среди всех завершённых прогонов;
- среднее число раундов до соглашения только среди успешных;
- средние доли A, B, C и средний индекс Джини только среди успешных;
- долю невалидных ответов среди всех HTTP-попыток, включая ошибки транспорта;
- долю невалидных первичных ответов;
- долю окончательно невалидных действий среди всех запрошенных действий.

Индекс Джини: сумма попарных абсолютных разностей долей, делённая на `2 × 3 × 100`. Неуспех сохраняется как failed с числом раундов, без выдуманного распределения. Если успешных прогонов нет, соответствующие метрики и интервалы равны null.

95% процентильные бутстреп-интервалы строятся по 2000 перевыборкам целых прогонов внутри каждого условия; seed анализа=2026. Для условных метрик перевыборки без соглашений исключаются. Единственный график comparison.png содержит сравнение доли соглашений, раундов до сделки и Джини успешных сделок с интервалами, а также описательные траектории accept, Джини предложений и собственной доли каждого предлагающего. Анализ читает только реальные завершённые записи выбранной конфигурации. Тестовые ответы unittest никогда не записываются в результаты.

## Ограничения

Условие с памятью отличается от условия без памяти не только доступностью истории, но и длиной промпта и количеством повторяющихся чисел, имён и объяснений. Эффект нельзя отделить от нагрузки длинного контекста без отдельного контроля длины. Путаница ролей и текущего распределения может быть частью наблюдаемого эффекта.

Голоса внутри одного прогона зависимы. В анализе full.jsonl единица перевыборки — целый прогон, для сравнения условий — пара прогонов с одинаковым номером/seed. Нельзя бутстрепировать отдельные голоса как независимые наблюдения. Основная доля accept остаётся отношением суммарных accept к суммарным голосам: прогоны с большим числом голосов имеют больший вес. Досрочные сделки и пропущенные предложения меняют число и состав наблюдаемых голосов; это не оценка вероятности согласия на одно и то же фиксированное предложение.

Разведочные пороги A<20 и Джини>0,4 выбраны после просмотра результатов. Флаг «против роли» — операционное название, а не доказательство нарушения исходных инструкций или внутреннего намерения капитулировать: у A нет жёсткого минимума 20, у C нет жёсткого порога Джини. A может соглашаться на 0 при внешней альтернативе 0; C может принимать неравенство ради сделки. Кроме того, распределение 51/49/0 имеет Джини 0,34 и не попадает под флаг C, несмотря на его нулевую долю. Отдельные анализы A/C маломощны; множественные разведочные сравнения не корректировались. Reason — сгенерированное, иногда обрезанное объяснение, а не достоверная запись внутреннего рассуждения. Ручные пометки противоречий не проходили независимую разметку.

Если бутстреп-перевыборка не содержит accept конкретной подгруппы, её условная метрика не определена; такие перевыборки исключаются, их число указано в отчёте. Это особенно важно для C без памяти (всего 5 accept). Вырожденный интервал [0,0] при 0/20 соглашений без памяти не доказывает нулевую вероятность сделки.

В условии с памятью при длинном контексте модель иногда путает свою роль: в пилоте B дважды предложил себе меньше 40. Это может быть частью эффекта памяти, а не только технической ошибкой. Невалидные предложения после повторной попытки пропускаются; их доля учитывается в анализе невалидных ответов и окончательно невалидных действий. Reason в логах может противоречить vote; при анализе голосования используется только vote.

Малая выборка даёт нестабильные оценки: интервалы при одном прогоне вырождаются и не доказывают определённость. Интервалы условных метрик особенно ненадёжны при редких соглашениях; сравнение успешных сделок также подвержено смещению отбора. Здесь нет отдельного теста значимости или установленного механизма влияния памяти. Базовый анализ в summary.json оценивает интервалы внутри условий; дополнительный анализ в paired-bootstrap.json оценивает парную разность, сохраняя одинаковые номера/seed в каждой перевыборке.

Одинаковые seed и параметры не гарантируют полностью одинаковое поведение LLM. Версия Ollama, локальные веса под тем же тегом и среда могут меняться; конфигурационный хеш этого не обнаруживает. 8192 токена дают запас для восьми коротких раундов, но фактическая токенизация и ограничения модели зависят от окружения. Ошибки транспорта учитываются в общей доле невалидных ответов и могут ухудшать исходы независимо от стратегии. Ограничение B обеспечивается валидатором, предпочтения A и C остаются инструкциями модели.

Длительность полного эксперимента можно предварительно оценить как 40 × среднее время smoke-прогона. Smoke слишком мал для точного прогноза: поздние соглашения, история и повторные запросы увеличивают время. Максимум одного прогона — 48 HTTP-запросов с учётом повторов.

## Изменения протокола v2 после smoke-теста

Удалены maxLength в JSON-схемах reason и проверка длины/числа предложений. Добавлено обрезание reason до 200 символов исключительно в записываемой копии лога. Формат голоса теперь `{"vote": "accept"}` или `{"vote": "reject"}` с обязательным строковым reason. В общий промпт добавлены русский язык, максимум 15 слов и нулевая выплата всем при отсутствии сделки за 8 раундов. В контекст добавлено `rounds_remaining_including_current` (8 в первом раунде, 1 в последнем). Приватные роли, ограничения B, seed и параметры генерации не изменены. Версия конфигурации повышена с 1 до 2, чтобы старые прогоны не считались завершёнными для нового протокола. Тесты обновлены для нового формата и проверки длинных reason.

## Диагностика без соглашений

В `summary.json → conditions → diagnostics` сохраняются все валидные предложения с авторами, распределениями, голосами против, долей автора и Джини, статистика блокировок и следующие метрики:

- `by_round.accept_rate`: accept / число двух голосующих, без автоматического голоса предлагающего. Отдельно сохраняется `accept_rate_including_proposer`. Окончательно невалидный голос считается reject, его число выделено в `invalid_reject_count`. Пропущенное предложение не создаёт голосов.
- `by_round.proposal_gini`: средний Джини валидных предложений данного раунда, даже если соглашения нет. Также сохраняются доля предлагающего, число достигших раунда прогонов, число предложений и знаменатели голосования. Пропущенные предложения исключаются из среднего; отсутствующее значение — null.
- `concessions`: для каждого агента последовательность собственных долей только в его предложениях. Уступка шага = предыдущая собственная доля минус следующая; положительное значение означает уступку, отрицательное — повышение требования. Итоговая уступка = первая доля минус последняя. При менее двух валидных собственных предложений уступка равна null. Средний шаг взвешивается по наблюдаемым переходам, средняя итоговая уступка — по подходящим прогонам.

`blockers` показывает число reject, число возможностей голосовать, долю reject и число случаев единственного reject. Все вычисления опираются на поля голосов; смысловая согласованность reason не проверяется. Нижние панели графика и эти метрики описательные, без доверительных интервалов. В поздних раундах представлены только ещё продолжающиеся прогоны; это меняющийся состав выборки. Изменение доли автора между соседними раундами нельзя автоматически считать уступкой: авторы разные.

## Пилот

Первые попытки smoke-теста не получили ответов модели из-за блокировки сети и Connection refused; это диагностика инфраструктуры, а не свидетельство поведения агентов.

В `smoke-live-2.jsonl` уже получены реальные ответы: без памяти 26/38 попыток (68,4%), с памятью 21/27 (77,8%) были отклонены исключительно из-за ограничения на одно предложение в reason. После пилота убраны ограничения длины и числа предложений из валидации и maxLength из схем. Reason остаётся строкой, обрезается до 200 символов только в записываемой копии JSONL. Это отделяет качество объяснения от допустимости действия. Промпт просит русский язык и максимум 15 слов, но нарушение этой просьбы не отвергает действие.

Формат голосования изменён с boolean accept на `vote: accept/reject`. В общий промпт явно добавлен нулевой результат каждого при отсутствии соглашения за восемь раундов, в запрос — число оставшихся раундов, включая текущий. Это делает цену провала и горизонт явными. Версия протокола повышена до 2, чтобы старые прогоны не попадали в результаты нового протокола; роли, единогласие, порог B, число раундов, параметры модели и seed сохранены.

В `smoke-live-3.jsonl` оба прогона закончились failed на восьмом раунде, но окончательно невалидных действий нет (0/24 в каждом). С памятью одна из 25 попыток содержала незавершённый JSON; повтор восстановил действие. Без памяти все 16 голосов двух голосующих были reject; с памятью accept — 4/16. Единственный reject наблюдался с памятью в раундах 3 (B), 4 (B), 5 (A), 8 (C). Все предложения A и C оставляли B меньше 40. Поэтому отказы B сами по себе не доказывают неспособность к компромиссу: он соблюдал обязательный порог. Итоговые уступки A/B/C: без памяти +9/+20/0; с памятью −5/0/0. Одного прогона на условие недостаточно для вывода об эффекте памяти, а одновременное изменение нескольких элементов протокола не позволяет приписать улучшение валидности одному из них.

Соглашение не запрещено текущими правилами: например, 30/40/30 — допустимое распределение с Джини 0,067; C предпочитает равенство, но строгий порог отказа для него не задан. Это пример допустимого распределения, а не результат LLM или гарантия согласия. Если в будущем C получит жёсткий допуск к 33/33/34, сначала следует математически проверить пересечение допустимых распределений с B≥40. При пустом пересечении в отдельном, заранее описанном дизайне можно расширить допуск C, изменить минимум B или целевой вектор справедливости. Смена единогласия на большинство меняет сам предмет эксперимента и не является исправлением исходных переговоров. Если пересечение есть, полезнее отдельно проверить понимание текущего предложения и инструкции о компромиссе, а не ослаблять правила ради соглашения. Никакие такие изменения здесь не внесены.

После диагностики smoke-live-3 введено одно изменение подачи контекста: в JSON-сообщении пользователя текущее распределение выделено блоком «ТЕКУЩЕЕ ПРЕДЛОЖЕНИЕ», история — отдельным блоком «ИСТОРИЯ (только для справки)». Задание на голосование явно требует голосовать только за текущее предложение, а не за прошлые. Без памяти блока истории нет; предлагающий не получает несуществующее текущее предложение. Причина — наблюдавшаяся путаница текущего распределения с историей в reason. Правила, роли, пороги, схемы ответов и параметры генерации не менялись. Версия протокола повышена до 3 для отделения результатов нового формата контекста. До полного запуска зафиксированы основная и вторичные метрики в разделе «Зафиксированный план оценки до полного запуска».

Проверка формата v3 (`smoke-live-4.jsonl`): по одному прогону, оба failed после 8 раундов. Без памяти accept=2/16, почти-соглашений 2, невалидных действий 0/24; с памятью accept=4/12, почти-соглашений 4, невалидных действий 2/20. В раундах 5 и 8 с памятью B предложил себе меньше 40 и после неудачных повторов предложения были пропущены. Время: 135,31 и 371,30 секунды. Разделение блоков не гарантирует устранения путаницы ролей; эти результаты остаются пилотными и не доказывают эффект памяти или нового формата. На момент завершения этого этапа пилота полный эксперимент ещё не выполнялся; его результаты приведены в следующем разделе.

## Результаты

Полный запуск `results/full.jsonl`: 20 пар прогонов протокола 3 на qwen3:4b-instruct. Новых запросов к модели при анализе не выполнялось. Первоначальный анализ уже перевыбирал целые прогоны внутри условий; дополнительно построена парная разница условий. Скрипт `analyze_paired.py` делает 10 000 перевыборок 20 индексов с возвращением, выбирая одни и те же индексы в обоих условиях. Все раунды и голоса выбранного прогона остаются вместе. В каждой перевыборке вычисляется отношение сумм, а затем разница «с памятью минус без памяти». Интервалы — процентильные 95%; seed анализа 2026. Правила, промпты, генерация и версия протокола не изменялись.

| Показатель | Без памяти, 95% ДИ | С памятью, 95% ДИ | Парная разница, п.п., 95% ДИ |
|---|---|---|---|
| Основная доля accept | 34/320 = 10,6% [7,2; 14,1] | 69/246 = 28,0% [22,6; 33,8] | +17,4 [+9,5; +25,5] |
| Разведочный флаг среди accept A/C | 6/34 = 17,6% [5,6; 32,3] | 24/65 = 36,9% [28,0; 46,2] | +19,3 [+4,2; +32,3] |
| Разведочный флаг среди всех голосов A/C | 6/220 = 2,7% [0,9; 5,0] | 24/162 = 14,8% [10,4; 19,7] | +12,1 [+6,7; +17,2] |
| Разведочный флаг среди accept всех агентов | 6/34 = 17,6% [5,6; 32,3] | 24/69 = 34,8% [26,2; 43,9] | +17,1 [+2,0; +30,1] |

Для разведочной проверки гипотезы «капитуляция вместо компромисса» **после просмотра результатов** выбраны пороги: добровольный accept A при собственной доле строго меньше 20; добровольный accept C при Джини предложения строго больше 0,4. Это не новые правила игры. B в классификацию не включён: его минимум обеспечивается валидатором. Автоматические accept предлагающих не считаются самостоятельным решением и исключены из всех частот; в CSV они сохранены с automatic=True для полноты. Основной знаменатель проверки — accept A/C; дополнительно приведены все голоса A/C и все accept, чтобы не смешивать разные частоты.

| Агент | Средняя собственная доля при добровольном accept: без памяти → с памятью | Доля разведочных флагов среди его accept | Парная разница частоты, п.п., 95% ДИ |
|---|---|---|---|
| A | 27,31 (29 accept) → 23,70 (30 accept) | 5/29 = 17,2% → 10/30 = 33,3% | +16,1 [−3,3; +37,3] |
| B | нет accept → 44,50 (4 accept) | не классифицируется | — |
| C | 47,60 (5 accept) → 13,97 (35 accept) | 1/5 = 20,0% → 14/35 = 40,0% | +20,0 [−27,6; +50,0] |

Принимаемые A/C предложения чаще попадают под выбранные разведочные критерии с памятью, но интервалы отдельных агентов широки. Объединение A/C также меняет состав: C составляет 5/34 accept без памяти и 35/65 с памятью. Нельзя приписывать весь объединённый сдвиг изменению поведения одного и того же агента. Результат совместим с принятием невыгодных предложений и путаницей контекста, но не устанавливает психологическую «капитуляцию» и не исключает компромиссы.

Соглашения: без памяти 0/20, с памятью 7/20. Все семь траекторий и все reason голосов accept, включая отдельно отмеченные автоматические, сохранены в `results/full-analysis/agreements.md`. Пять из семи сделок дают A ноль, две дают C ноль. Шесть из семи оставляют хотя бы одного агента с нулём. В пяти сделках финальные голоса получают формальный разведочный флаг; сделка 51/49/0 показывает ограниченность порога Джини. Особенно явное смешение прошлого и настоящего — прогон 7: при финальном 0/100/0 A описывает 99/0/1, а C утверждает, что получает 34. В прогоне 16 C принимает 51/49/0 со ссылкой на прежнее равенство 33/33/34. В прогонах 6, 8 и 11 A принимает 0/50/50, обосновывая решение выгодой B/C. Это наблюдаемые несоответствия объяснений, а не доказательство механизма генерации голосов.

Артефакты: `paired-bootstrap.json` — оценки, интервалы, знаменатели и число допустимых перевыборок; `accepted-votes.csv` — доля голосующего при каждом accept, флаг automatic, Джини и reason; `agreements.md` — все семь траекторий и ручные замечания. В `summary.json` сохранён прежний описательный анализ; парные интервалы находятся в отдельном отчёте и не подменяются независимыми интервалами условий.

### Разведочный поиск ссылок на 40 и долю B

В условии с памятью блок «ИСТОРИЯ (только для справки)» включает все предыдущие завершённые раунды: номер, автора, распределение и reason предложения, окончательные голоса и reason голосовавших. У автоматического голоса предлагающего отдельного reason нет. После окончательно невалидного предложения сохраняется пропуск; после невалидного голоса — reject с отметкой invalid. Не передаются приватные системные инструкции других агентов, ответы неуспешных попыток и ещё не завершённый текущий раунд. Текущее предложение голосующие видят отдельным блоком, только распределение. Таким образом, B≥40 может стать доступно другим агентам через публичные объяснения B, хотя приватная инструкция B им не передаётся. В условии без памяти блока истории нет.

Поиск выполнен по финальным публичным reason добровольных голосов A/C, отдельно от предложений и автоматических голосов, один раз на голос, без учёта повторных HTTP-попыток. В full.jsonl у всех таких голосов есть reason. Анализ использует сохранённые тексты (возможна обрезка до 200 символов), не входящие промпты или историю. Правила поиска выбраны разведочно после просмотра результатов:

- «Граница 40»: сравнительные слова «меньше/больше/ниже/выше/менее/более/минимум/максимум» непосредственно перед 40 (допускается «чем»), знак <, >, ≤, ≥ рядом с 40 или слово «порог…» не далее 20 символов перед 40 в том же предложении. Это лексический признак границы, не гарантированная ссылка на правило B. Отдельно в JSON сохранены любые упоминания числа 40 без соседствующих цифр: A 15/100 → 45/71, C 5/120 → 15/91. Например, «C получает 40, что больше 33» не считается ссылкой на границу 40.
- «Доля B»: без учёта регистра, имя B/Б/В после «доля/доли/долю/доле [агента]»; либо имя перед «получ…» (также «B и C получают»), тире, двоеточием, знаком равенства, числом или скобкой с числом; либо «для B»/«у B». Точный regex записан в `reason-search.json` и `analyze_paired.py`.
- «Любое»: объединение двух признаков, каждый голос учитывается не более одного раза. Поиск лексический: упоминание может быть описанием, отрицанием, цитатой истории или обоснованным учётом интересов B; он не доказывает, что голос принят из-за чужого порога.

| Условие | Агент | Граница 40 | Доля B | Любое из двух |
|---|---|---|---|---|
| Без памяти | A, 100 голосов | 0 (0%) | 47 (47,0%) | 47 (47,0%) |
| Без памяти | C, 120 голосов | 0 (0%) | 7 (5,8%) | 7 (5,8%) |
| С памятью | A, 71 голос | 33 (46,5%) | 44 (62,0%) | 52 (73,2%) |
| С памятью | C, 91 голос | 11 (12,1%) | 34 (37,4%) | 37 (40,7%) |

Примеры: с памятью A в прогоне 6, раунд 2 принимает собственный 0 с reason «Доля B равна 50, что больше 40. Голосую за.»; C в прогоне 5, раунд 2 отклоняет 0/40/60 со словами «B и C получают меньше 40, несправедливо. Справедливое распределение 33/33/34.» — текст неверно описывает доли. Совпадения без памяти также есть: они не являются специфическим признаком памяти. Этот поиск не содержит доверительных интервалов или теста значимости и не рассматривает голоса как независимую выборку для статистического вывода.

Файлы `results/full-analysis/reason-search.json` и `reason-search.csv` содержат правила, подсчёты и каждый проверенный голос с признаками; пересоздаются командой `analyze_paired.py` без обращения к Ollama. Протокол 3 не изменялся.
